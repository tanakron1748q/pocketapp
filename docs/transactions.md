# เพิ่ม ดู แก้ไข และลบรายการส่วนตัว — issue #3–4

เปิด `/dashboard` หลังเข้าสู่ระบบเพื่อเพิ่มรายรับหรือรายจ่าย เลือกหมวดส่วนตัวของประเภทนั้น จำนวนเงิน วันที่ และคำอธิบายที่ไม่บังคับ วันที่เริ่มต้นอ้างอิง server ตาม `Asia/Bangkok` จึงไม่เปลี่ยนตาม timezone ของอุปกรณ์

ต้องตั้งค่า Google/Neon ตาม [คู่มือระบบเข้าสู่ระบบ](auth-setup.md) และรัน `pnpm db:migrate` ก่อนใช้งาน Migration ใหม่ `20261028000200_transactions` เพิ่มตาราง `categories` และ `transactions` โดยไม่เปลี่ยนตาราง auth เดิม

## กติกา

- หมวดตั้งต้นส่วนตัว: รายรับ 3 หมวด (เงินเดือน รายได้เสริม รายรับอื่น ๆ) และรายจ่าย 6 หมวด (อาหารและเครื่องดื่ม เดินทาง ที่อยู่อาศัย ซื้อของ สุขภาพ รายจ่ายอื่น ๆ)
- เมื่อเปิดหมวดครั้งแรก ระบบสร้างหมวดให้ User นั้น การเปิดพร้อมกันหลายอุปกรณ์ไม่สร้างหมวดซ้ำ โดยมี unique constraint ของ `userId` และ `starterKey`
- รับจำนวนเงินเป็นข้อความเลขฐานสิบ เช่น `0.01`, `12.3`, `123.45` ไม่รับ comma, exponent, ค่าศูนย์/ติดลบ หรือทศนิยมเกินสองตำแหน่ง
- เก็บเป็น `INTEGER` หน่วยสตางค์ ช่วง 0.01–21,474,836.47 บาทต่อรายการ ไม่มีการคูณเลขทศนิยมแบบ floating point และฐานข้อมูลมี CHECK ว่าจำนวนเงินเป็นบวก
- เก็บ business date เป็น PostgreSQL `DATE` ส่งผ่าน API เป็น `YYYY-MM-DD` แยกจากเวลาสร้าง/แก้ไข (`TIMESTAMPTZ`) รับวันนี้หรือย้อนหลังตามเวลาไทย ตรวจวันจริงและปีอธิกสุรทิน
- คำอธิบายยาวได้ไม่เกิน 1,000 ตัวอักษร ตัดช่องว่างหัวท้าย และเก็บข้อความว่างเป็น `null`
- รายการเรียงวันที่ล่าสุดก่อน แล้วเวลาที่บันทึกล่าสุดก่อน และ ID เป็นตัวตัดสินลำดับเมื่อเวลาตรงกัน โหลดครั้งละ 20 รายการ
- เมื่อบันทึกล้มเหลวฟอร์มยังเก็บข้อมูลร่างไว้ เมื่อบันทึกสำเร็จล้างเฉพาะจำนวนเงินและคำอธิบายเพื่อกรอกรายการถัดไป

## แก้ไขและลบ

กด **แก้ไข** ในรายการ ระบบโหลดข้อมูลล่าสุดจาก server ก่อนเติมฟอร์ม แก้จำนวนเงิน วันที่ หมวด และคำอธิบายได้ตามกติกาเดิม โดยคงประเภทรายรับ/รายจ่ายเดิมไว้ หมวดที่เลือกได้ต้องเป็นของตนเองและตรงกับประเภทของรายการ การกดยกเลิกไม่บันทึกร่าง

กด **ลบ** เพื่อดูข้อมูลรายการที่จะลบ แล้วกด **ยืนยันลบรายการ** จึงจะส่งคำขอ การกดยกเลิก ปิดหน้าต่าง หรือกด Escape ก่อนยืนยันไม่เปลี่ยนข้อมูล ระหว่าง server กำลังบันทึก/ลบ ปุ่มจะระบุสถานะและป้องกันการกดซ้ำ

ระบบแสดงผลสำเร็จและเปลี่ยนรายการบนหน้าจอหลัง server ยืนยันแล้วเท่านั้น เมื่อแก้ไขหรือลบล้มเหลว หน้าต่างยังเปิดพร้อมข้อความให้ลองใหม่ ร่างแก้ไขและรายการเดิมยังอยู่ หาก server บันทึกสำเร็จแต่โหลดรายการใหม่ไม่สำเร็จ จะแสดงผลที่ยืนยันแล้วพร้อมข้อผิดพลาดการโหลดแยกกัน

## HTTP contract

ทุก endpoint ใช้ session cookie ของผู้ใช้และตอบ `Cache-Control: private, no-store` ไม่รับ `userId` สำหรับกำหนดเจ้าของข้อมูล

`GET /api/categories` ส่ง `{ categories: [{ id, name, type, archived }], today: "YYYY-MM-DD" }` โดยสร้างหมวดตั้งต้นที่ยังไม่มีให้เฉพาะผู้ใช้คนนั้น

`GET /api/transactions` ส่ง `{ transactions, nextCursor }` รายการแต่ละตัวมี `id`, `type`, `amount` (ข้อความบาทสองตำแหน่ง), `date`, `description`, `category: { id, name, type, archived }` หากมีหน้าถัดไป เรียก `GET /api/transactions?cursor=LAST_ID` โดย cursor ต้องเป็นรายการของผู้ใช้คนนั้น

`POST /api/transactions` ต้องส่ง JSON พร้อม `Origin` ที่ตรงกับ `BETTER_AUTH_URL`:

```json
{
  "type": "EXPENSE",
  "amount": "123.45",
  "categoryId": "ID จาก GET /api/categories",
  "date": "2026-10-28",
  "description": "อาหารกลางวัน"
}
```

ใช้ `type: "INCOME"` สำหรับรายรับ และละ `description` ได้ สำเร็จตอบ 201 พร้อม `{ transaction }` ข้อมูลต้องผ่าน Zod และตรวจหมวดด้วย `categoryId`, `session.user.id` และประเภทพร้อมกัน ฐานข้อมูลบังคับความสัมพันธ์แบบ composite foreign key ซ้ำอีกชั้น จึงอ้างหมวดของ User อื่นหรือผิดประเภทไม่ได้

`GET /api/transactions/ID` อ่านรายการของตนเอง ส่ง `{ transaction }` ไม่พบหรือเป็นของคนอื่นตอบ 404 แบบเดียวกัน

`PUT /api/transactions/ID` ส่งรายละเอียดที่แก้ได้ครบชุดเป็น JSON พร้อม `Origin` ที่ตรงกับ `BETTER_AUTH_URL`:

```json
{
  "amount": "99.01",
  "categoryId": "ID หมวดของตนที่ตรงกับประเภทเดิม",
  "date": "2026-10-27",
  "description": "แก้จำนวนเงิน"
}
```

สำเร็จตอบ 200 พร้อม `{ transaction }` ละ `description` ได้เพื่อทำให้คำอธิบายว่าง ไม่รับ `type`, `userId`, `id` หรือ field อื่น ประเภทเดิมอ่านจากแถวที่ตรวจเจ้าของแล้ว

`DELETE /api/transactions/ID` ต้องส่ง `Origin` เช่นเดียวกัน สำเร็จตอบ 200 พร้อม `{ deleted: true }` ไม่มีการลบหมวดหรือรายการของคนอื่น การลบซ้ำตอบ 404

ข้อผิดพลาด: 401 ไม่มี session, 403 origin ไม่ถูกต้อง, 415 ไม่ใช่ JSON, 400 JSON/พารามิเตอร์ไม่ถูกต้อง, 404 รายการหรือ cursor ไม่ใช่ของตนหรือไม่มีอยู่, 422 ข้อมูลไม่ผ่านกติกา (พร้อม `fields`), 503 เชื่อมต่อ/จัดเก็บไม่สำเร็จ ข้อความข้อผิดพลาดไม่ส่งรายละเอียดฐานข้อมูลหรือ token กลับ client

## จุดเชื่อมต่อระบบเงินคืนใน ticket ถัดไป

เส้นทางแก้/ลบทั้งหมดใช้ `editOwnedTransaction()` และ `deleteOwnedTransaction()` ใน `src/lib/transactions.ts` โดยเปิด database transaction และล็อกแถวของรายการด้วย `lockOwnedTransaction()` (`SELECT ... FOR UPDATE` ที่มีทั้ง ID และ User ID) ก่อนตรวจหมวดและเปลี่ยนข้อมูล ไม่ใช้ upsert จึงไม่สร้างรายการที่ลบไปแล้วกลับมา

เมื่อเพิ่มเงินคืน ต้องเพิ่มการตรวจยอดคืนสะสมและข้อจำกัดการลบ/แก้รายจ่ายใน database transaction เดียวกันที่จุดนี้ ก่อน mutation และให้เส้นทางสร้าง/แก้/ลบเงินคืนล็อกรายจ่ายต้นทางแถวเดียวกันก่อนตรวจยอดด้วย การตรวจคนละ transaction หรือเพิ่ม endpoint ที่ bypass จุดนี้จะไม่รักษากติกาเมื่อคำขอมาพร้อมกัน

ขณะนี้ยังไม่มี model เงินคืนหรือการตรวจยอดคืนสะสม ticket #4 ไม่ได้อ้างว่าใช้กติกาเงินคืนได้แล้ว และไม่มี migration ใหม่เพิ่มจาก ticket #3

## การทดสอบ

รัน `pnpm test:e2e` เพื่อสร้าง PostgreSQL container แยก รัน migration ทั้ง auth และรายการ และทดสอบ production server ผ่าน browser/HTTP บน desktop/mobile:

- ฟอร์มเพิ่มรายจ่าย/รายรับ เลือกหมวดตามประเภท วันที่เริ่มต้น และคำอธิบายที่ไม่บังคับ
- การเปลี่ยนประเภทล้างหมวดเดิม การบันทึกแล้ว reload และอีก session/อุปกรณ์ของ User เดิมเห็นข้อมูลตรงกัน
- จำนวนเงินถึงสตางค์ ค่าสูงสุด ข้อมูลไม่ถูกต้อง วันที่เป็นไปไม่ได้ วันในอนาคต และข้อมูลที่พยายามปลอมเจ้าของ
- การอ่านและสร้างรายการข้าม User, หมวดผิดประเภท, cursor ของคนอื่น และ cross-origin POST
- หมวดตั้งต้นไม่ซ้ำเมื่อเข้าใช้พร้อมกัน การเรียงลำดับและ pagination
- สถานะไม่มีข้อมูล กำลังบันทึก โหลดล้มเหลว ลองใหม่ และรักษาร่างเมื่อบันทึกไม่สำเร็จ
- แก้เงิน/วันที่/หมวด/คำอธิบายของรายรับและรายจ่ายแล้วอ่านผลจริงจากอีก session รวมถึงการล้างคำอธิบาย
- อ่าน/แก้/ลบผ่าน ID ของคนอื่นถูกปฏิเสธ หมวดผิดประเภท/ของคนอื่น และการปลอมเจ้าของไม่เปลี่ยนข้อมูลเดิม
- ยกเลิกหน้าต่างแก้/ลบไม่เปลี่ยนข้อมูล ยืนยันลบแล้ว reload ไม่พบรายการ
- การแก้ข้อมูลไม่ผ่าน validation คำขอแก้/ลบล้มเหลว การโหลดรายการแก้ไขล้มเหลว และการกดลองใหม่
- คำขอแก้และลบพร้อมกันไม่สร้างรายการที่ลบแล้วกลับมา และผลที่บันทึกจริงยังแสดงถูกต้องเมื่อ refresh รายการล้มเหลว

ชุดทดสอบใช้ session fixtures ในฐานข้อมูลแยก ไม่มี test-login endpoint ในแอป และไม่ได้ยืนยัน Google OAuth จริง การตรวจบน cloud ยังต้องตั้งค่าบริการก่อน

ตรวจด้วยบัญชีจริงหลัง deploy: เพิ่มรายการจากมือถือแล้ว reload desktop ด้วย Google เดิม ตรวจวันและจำนวนเงินตรงกัน จากนั้นสลับ Google อีกบัญชี ต้องไม่เห็นรายการเดิมหรือเลือกหมวดของบัญชีเดิมได้

ตรวจแก้/ลบหลัง deploy ด้วย: เปิดรายการจากบัญชี A แก้จำนวนเงิน/วันที่/หมวด/คำอธิบายแล้ว reload อีกอุปกรณ์ จากนั้นยกเลิกหน้าต่างลบหนึ่งครั้งก่อนยืนยันลบ ตรวจว่าข้อมูลบัญชี B ยังอยู่ และส่ง HTTP ด้วย ID ของ B จาก session A ต้องได้ 404

ขอบเขตนี้ยังไม่มีการค้นหา/กรอง งบ เงินคืน หรือยอดสรุป Dashboard ซึ่งอยู่ใน ticket ถัดไป

การจัดการหมวดส่วนตัวและกติกาหมวดที่เก็บแล้ว: [คู่มือ ticket #5](categories.md)

## รายการโปรด (Issue #7)

กรอกประเภท จำนวนเงิน หมวดหมู่ และคำอธิบายในฟอร์มเพิ่มรายการ แล้วกด **เก็บรายละเอียดในฟอร์มเป็นรายการโปรด** ตั้งชื่อและยืนยัน รายการโปรดจัดเก็บใน PostgreSQL แยกตามบัญชี ใช้บัญชีเดิมข้ามอุปกรณ์ได้ และไม่สร้างรายรับหรือรายจ่ายเมื่อเก็บรายการโปรด

กด **ใช้ …** เพื่อเติมฟอร์มร่าง ระบบตั้งวันที่เป็นวันนี้ตามเวลาไทย ไม่เก็บหรือนำวันที่เก่าจากฟอร์มต้นทางมาใช้ ผู้ใช้ต้องตรวจวันที่ จำนวนเงิน หมวดหมู่ และคำอธิบาย สามารถแก้ไขทั้งหมดก่อนกด **บันทึกรายการ** หรือกด **ยกเลิกร่าง** เพื่อทิ้งร่างโดยไม่สร้างธุรกรรม การแก้ร่างไม่เปลี่ยนรายละเอียดในรายการโปรด และการลบรายการโปรดไม่ลบธุรกรรมที่เคยบันทึก

API ส่วนตัว (ตอบ `Cache-Control: private, no-store`):

- `GET /api/favorites` โหลดรายการโปรดของบัญชีปัจจุบัน
- `POST /api/favorites` รับ `{ name, type, amount, categoryId, description? }` โดยใช้จำนวนเงินแบบ string และกติกาสตางค์เดียวกับธุรกรรม ชื่อหลังตัดช่องว่างยาว 1–100 ตัวอักษร ไม่รับ `date`, `userId` หรือ `transactionId`
- `GET /api/favorites/:id` อ่านรายละเอียดของบัญชีปัจจุบันเพื่อเติมร่าง ไม่มีการเขียนธุรกรรม
- `DELETE /api/favorites/:id` ลบรายการโปรดของบัญชีปัจจุบัน

หากหมวดในรายการโปรดถูกเก็บแล้ว การเรียกใช้จะเติมรายละเอียดอื่นแต่เว้นหมวดให้เลือกใหม่ก่อนบันทึก ไม่อนุญาตให้สร้างรายการโปรดใหม่ด้วยหมวดที่เก็บแล้ว

ทุก mutation ตรวจ session และ Origin หมวดต้องยังใช้งาน เป็นของบัญชีปัจจุบันและตรงประเภท โดยมี composite foreign key บังคับความสัมพันธ์ซ้ำในฐานข้อมูล การบันทึกธุรกรรมหลังใช้รายการโปรดยังผ่าน `POST /api/transactions` และตรวจข้อมูลใหม่ตามเดิม ไม่ใช่การยืนยันด้วย ID รายการโปรด

ทดสอบเฉพาะฟีเจอร์ด้วย `pnpm test:e2e favorites.spec.ts` ครอบคลุม browser บน desktop/mobile และ HTTP จริงกับ PostgreSQL แยกสำหรับทดสอบ รวมถึง prefill, วันที่ไทยแทนวันที่เก่า, แก้ก่อน save, cancel, ไม่มีการสร้างธุรกรรมอัตโนมัติ, แยกบัญชี/อุปกรณ์, หมวดผิดสิทธิ์/ประเภท, ข้อมูลไม่ถูกต้อง และการลองใหม่หลังโหลดหรือบันทึกล้มเหลว
