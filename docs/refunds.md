# เงินคืนอ้างอิงรายจ่าย

ใน `/dashboard` กด **เงินคืน / ประวัติ** ที่รายจ่ายเพื่อดูต้นทาง เงินคืนสะสม ยอดที่คืนได้อีก และประวัติเงินคืน เพิ่มเงินคืนบางส่วนหรือเต็มจำนวนได้หลายครั้ง แก้ไขจำนวนเงิน วันที่ได้รับจริง และคำอธิบายได้ ปุ่มลบเงินคืนมีหน้าต่างยืนยัน

เงินคืนใช้หมวดของรายจ่ายต้นทางเสมอ รวมถึงหมวดที่เก็บแล้ว หากแก้หมวดรายจ่าย เงินคืนจะตามหมวดใหม่ ไม่สร้างรายรับหรือหมวดแยกให้เงินคืน การย้ายเงินคืนไปอ้างอิงรายจ่ายอื่นต้องลบแล้วบันทึกใหม่

จำนวนเงินใช้สตางค์จำนวนเต็ม กติกาเดียวกับรายรับ/รายจ่าย: มากกว่า 0 ถึง 21,474,836.47 บาท ทศนิยมไม่เกิน 2 ตำแหน่ง รับวันที่จริงที่ไม่ใช่อนาคตตามเวลาไทย และคำอธิบายไม่เกิน 1,000 ตัวอักษร

## รายจ่ายสุทธิตามเดือน

ส่วนรายจ่ายสุทธิรายเดือนเริ่มที่เดือนปัจจุบันและเลือกเดือนย้อนหลังได้:

- รายจ่ายสุทธิ = รายจ่ายในเดือนนั้น − เงินคืนที่ได้รับในเดือนนั้น
- เงินคืนลดหมวดของต้นทางในเดือนที่ได้รับ ไม่ย้อนกลับไปเปลี่ยนยอดเดือนที่ซื้อ
- ตัวอย่าง: ซื้อ 100.25 บาทวันที่ 31 มกราคม รับคืน 40.01 บาทวันที่ 29 กุมภาพันธ์ มกราคมมีรายจ่ายสุทธิ 100.25 บาท กุมภาพันธ์มีรายจ่ายสุทธิ −40.01 บาท ถ้าไม่มีรายจ่ายอื่น
- ยอดรายรับไม่เพิ่มขึ้น เงินคืนมีประวัติและวันที่ของตนเอง

## API

ทุก endpoint ต้องมี session และตอบ `Cache-Control: private, no-store` ทุก mutation ต้องส่ง `Origin` ตรงกับ `BETTER_AUTH_URL`

- `GET /api/transactions/:expenseId/refunds` — `{ transaction, refunds, refunded, remaining }` ต้นทางและประวัติเรียงวันที่ล่าสุดก่อน
- `POST /api/transactions/:expenseId/refunds` — `{ amount, date, description? }` ตอบ `201 { refund }`
- `PUT /api/transactions/:expenseId/refunds/:refundId` — body แบบเดียวกัน ตอบ `{ refund }`
- `DELETE /api/transactions/:expenseId/refunds/:refundId` — ตอบ `{ deleted: true }`
- `GET /api/expense-summary?month=YYYY-MM` — `{ month, expense, refunded, netExpense, categories }` ค่าเริ่มต้นเดือนปัจจุบัน ค่าเงินเป็น decimal string เสมอ รายหมวดมี `id`, `name`, `expense`, `refunded`, `netExpense` แยกตามผู้ใช้และไม่รวมรายรับ

อ้างอิงรายรับ รายการไม่มีอยู่ หรือของผู้ใช้อื่นตอบ `404` ข้อมูลไม่ถูกต้องหรือยอดคืนเกินต้นทางตอบ `422` และอาจมี `fields` สำหรับฟอร์ม ฟิลด์เจ้าของ หมวด และต้นทางไม่รับจาก body

## การรักษายอดเมื่อใช้งานพร้อมกัน

Migration `20261029000100_refunds` เพิ่มตาราง `refunds` พร้อม FK ที่บังคับเจ้าของและประเภทรายจ่าย และ CHECK จำนวนเงินบวก/ประเภท EXPENSE

ทุก mutation ของเงินคืนและรายจ่ายต้นทางล็อกแถวต้นทางเดียวกันด้วย `FOR UPDATE` ก่อนอ่านยอดคืนใน PostgreSQL transaction การตรวจยอดและเขียนเกิดใน transaction เดียวกันที่ isolation `READ COMMITTED` จึงอ่านผล commit ของคำขอก่อนหน้าหลังรอล็อก ไม่มีการเรียกบริการภายนอกระหว่างถือ lock

ยอดคืนรวมต้องไม่เกินต้นทาง ห้ามลดต้นทางต่ำกว่ายอดคืนสะสม และห้ามลบต้นทางที่ยังมีเงินคืน ต้องแก้หรือลบเงินคืนที่ขัดกันก่อน การลบบัญชี cascade ทั้งรายจ่ายและเงินคืนของเจ้าของ

## ตรวจรับ

รัน `pnpm test:e2e` (ต้องเปิด Docker) เพื่อใช้แอป production build, browser/HTTP และ PostgreSQL แยกอัตโนมัติ ทดสอบทั้ง desktop/mobile, สอง session/ผู้ใช้, การคืนบางส่วน/เต็มจำนวน, วันที่/จำนวนเงินผิด, ข้ามเดือน/ยอดสุทธิติดลบ, หมวดที่แก้/เก็บแล้ว, การแก้/ลบ, ร่างเมื่อบันทึกล้มเหลว และคำขอเงินคืนชนกันหรือชนกับการแก้/ลบต้นทาง

ก่อนใช้กับฐานข้อมูลจริงรัน `pnpm db:migrate` และทำตามขั้นตอนตรวจ Google OAuth จริงใน [คู่มือตั้งค่า](auth-setup.md) การทดสอบอัตโนมัติใช้ session fixtures ไม่ใช่ OAuth จริง
